## 1. Executive overview

### 1.1 What JobFairX is (product model — never contradict this)

JobFairX runs **hiring events**. It is **NOT a job board** — that phrase is load-bearing in all
copy. The mechanic, in the order a first-time reader needs it:

1. An **employer registers for an event** (a market-and-audience moment, e.g. "Dallas Technology
   Hiring Event, September 10") and **posts jobs**. Jobs are *inside* the event package — there
   is no separate job-postings product.
2. The employer sets **screening questions** and **interview settings**.
3. **AI matches** registered candidates to those jobs using the screeners/must-haves.
4. **Matched candidates request an interview time.** The employer **accepts, declines, or
   proposes/suggests a different time**. **Auto-accept** can confirm instantly and pauses when
   interview slots are full. *Every interview is one both sides agreed to.*
5. Interviews happen **in person / on JobFairX video / by phone** — chosen per event in
   Interview Settings — and run **before, during, and after** the event date. **Never imply all
   interviews happen on event day.**
6. A **post-event report** is ready the moment the event ends: requests, scheduled, completed,
   missed, and the employer's **Yes / Maybe / No** rating per candidate.

**Interview location is a per-employer setting, not an event property.** Two employers at the
same Dallas Healthcare event can interview completely differently. "Your own link" (Teams, Zoom)
is a sub-choice *inside* Video, not a fourth format.

**The product does NOT track hires.** Never claim hires, time-to-hire, or ROI.

**Banned vocabulary in rendered copy:** "virtual" (except the `virtual.jobfairx.com` login URLs),
"apply / application / applicants" (except the live site's own job-board *contrast* copy — see
§7.4), "event format", "in-person events", "host your own event".

## 3. The marketing builder pipeline (architecture)

**Both marketing pages are generated by Python builders from frozen captures of the live site.
Edit the builder, never the HTML output.**

```
assets/live-capture/employer-live-dom.html      frozen rendered DOM of jobfairx.com/employer
assets/live-capture/event-detail-live-dom.html  frozen rendered DOM of the Dallas Tech event page
assets/live-capture/setup-cal-fragment.html     NEW this session — exact code lifted from the
                                                launching calendar design (§5.7)
        │
        ├── build-employer-home.py  ──→ employer-home.html
        │                                     │
        └── build-event-detail.py   ──────────┘ (imports sections FROM the built home)
                                    ──→ employer-event-detail.html
```

### 3.1 The `sub()` contract

Every replacement asserts its anchor matches **exactly once** and **aborts** otherwise, so drift
in the live capture fails loudly instead of silently shipping stale copy. A zero-count match must
abort (a double-space in a live title once made a count-derived expected value of 0 pass
silently).

### 3.2 Cross-builder coupling (critical)

`build-event-detail.py` **imports the built homepage's sections** — the How It Works section by
probing its H2 text, and (formerly) the bento by `id="built-in-tools"`. Therefore:

- **Any change to a homepage anchor breaks the event builder.** Update both in the same change.
- The event builder then applies a **localization layer** (`loc()`), replacing homepage strings
  with Dallas-Technology-specific ones (§5.2).
- **Run the home builder before the event builder**, always.
- **Proof-of-no-cascade technique used this session:** md5 the event output before and after a
  home-builder change; identical hash = no cascade.

### 3.3 Purged-Tailwind trap

The live site's compiled CSS lacks any utility the live pages never used (`right-2.5`,
`grid-cols-4` bit previous sessions). **For new markup use inline styles or a scoped `<style>`
block** — never bare Tailwind utilities.

## 4. Copy rules (Scott's, learned the hard way this session)

These are now also stored in auto-memory as `jobfairx-marketing-copy-rules`.

1. **Headings must be outcome-based**, never process instructions.
   - Rejected: "Register once, interview all day" (Scott: *"is dumb… it needs to be outcome
     based"*, and it misstated the model — interviews are not all on event day).
   - Rejected: "Post your jobs and let the interviews come to you" (instruction, not outcome).
   - Approved: "Interview on your terms: in-person, video, or phone".
2. **Feature jargon is banned in headings.** Scott on "Propose interview times": *"They don't
   know what that means until we educate them."* Teach the mechanic in the **body**, sell the
   outcome in the **heading**.
3. **No em dashes in headings** — use a colon. (Body-copy em dashes were never ruled on; Scott
   was asked and did not answer. Several remain in event-page body copy.)
4. **Format naming:** headings and bullets use the product's **bare labels** — "in-person, video,
   or phone" (matching the In-Person / Video / Phone pills). **Full prose sentences keep the
   prepositions** — "in person, on video, or by phone".
5. **"Applicants" → "candidates"** everywhere in our own copy. Exception: the live site's own
   job-board contrast copy ("Job boards give you applicants…", "✕ Passive applicants") stays
   verbatim — there it describes the job-board model, not JobFairX candidates.
6. **Where the page is the developer's reference for production, revert to the live site's copy
   verbatim.** Scott had the entire "Review and confirm interviews" step (heading + body + mock)
   reverted to production's exact version so the developer sees what production says today.
7. **No motion.** See §9.1 — this was tested and rejected on a live demo.
8. Sentence case; "Register" is the only commitment verb, "See" the only exploration verb.
9. Never invent numbers, dates, or counts — use a visible placeholder for Scott to fill.

## 6. Research findings (evidence base — do not re-run)

### 6.1 Homepage vs landing-page duplication (5-agent study)

**The live jobfairx.com site:** ~56% of an event page's visible text is verbatim-shared with the
homepage, ~9% is event-template chrome, ~35% is type/city-specific. **How It Works and Built-in
Tools repeat with identical wording; only the mock DATA is localized per event** (candidate names,
roles, cities). Event pages drop the homepage's first step. Between a tech and a healthcare event
page, what varies: title/H1/subhead, hero date and stats, hero logo marquee, all testimonial
quotes, Past Companies logos, closing CTA + show-rate stat, every mock persona.

**Stripe (verified from served HTML):** **zero** full prose sections repeat between homepage and
product pages. Reuse is chrome + one shared stat + one demo widget with entirely different copy
around it. Homepage product cards are **heading + graphic only, no body copy**. Each capability
gets **one** deep page; everywhere else it's a one-sentence card with page-tuned angle and even
page-tuned statistics (checkout uplift is "11.9%" on payments, "2%–3%" on billing).

**Linear:** one repeated paragraph site-wide; a canonical short headline per pillar reused as the
linking thread (homepage H2 → inner page H1/title). **Vercel:** zero shared marketing copy.

**Programmatic/template pages (Zapier, Eventbrite, Calendly):** template pages share only chrome
verbatim; every body block is segment-specific data or a **re-angled, compressed** version of the
product story. Each self-canonicalizes. **Takeaway adopted:** keep one locked skeleton, localize
the proof layer deeply, compress the product story rather than repeating the homepage's.

### 6.2 How multi-mode products show one visual for several modes (2-agent study)

**Hiring platforms (HireVue, Paradox, Greenhouse, Indeed, Ashby, Lever): in-person interviews are
visually invisible — zero pixels, on all six.** Indeed writes "Schedule a video, phone, or
in-person interview" as body copy with no matching image. Paradox renders onsite interviews as
scheduling UI. **No site pairs in-person photography with video-UI screenshots as a format
contrast.** Where a format is labeled visually, the label is **diegetic UI chrome** (HireVue's
"Video Interview" pill inside the mock), never a marketing badge.

**Communication platforms (Zoom, Teams, Webex):** mode breadth lives in an interactive
**structure** (tabs, carousel, icon chips), one mode per frame, with copy carrying the
enumeration. Physical rooms are the odd mode out — shown as environment photography in their own
slot, or folded into the meeting UI as one named tile.

**Scott's challenge to this** (*"probably they only offer video interviews"*) was partly fair —
none of those companies makes multi-format its headline differentiator, which JobFairX does. Three
adapted design options were mocked (§10.2) and remain **undecided**.

## 9. Lessons learned this session

### 9.1 The motion experiment — settled, do not revisit

Scott admired `cybernervetech.info` (*"very interactive… engaging and fun"*) and asked for a full
motion exploration citing Salesforce. I built one (scroll reveals, count-ups, drifting chips,
hover cards) and published it as an artifact. **He viewed it and rejected it outright: "I do not
like it. No motion. You could delete that."** Files deleted; decision recorded in auto-memory.
The site is a **static designed-state** page. The only animation anywhere is the calendar's
Live-pill pulse, which is the launching design's own code.

### 9.2 Measure the child, not the container

Two clipping bugs shipped because checks measured row boxes rather than the button inside them
(§2.5). Scott caught both from screenshots. Always measure the deepest child's right edge against
the clipping frame, at multiple widths.

### 9.3 Whitespace in anchors

An event-builder anchor failed because the live capture had **12 spaces** after a newline and the
anchor had 10. When an anchor aborts at 0 matches, print the exact `repr()` of the string from the
built file rather than guessing.

### 9.4 A JS renderer can silently override your markup

The healthcare dashboard's location cell is rewritten at runtime from a JS map (§5.14). Static
markup looked right and rendered wrong. **When a prototype's cell renders differently than the
HTML says, grep for a JS map keyed by a data attribute.**

### 9.5 Show the example before building

Scott asked for chat examples repeatedly ("Give me an example in the chat before we create a
file"). Every build that started with a mock landed; the one that skipped it (the motion demo) was
rejected wholesale.

### 9.6 "Use what's on the live site" means the whole section

§5.6 — heading, body, and visual, not just the paragraph.

## 12. ⚠️ MAIN V3 AND HEALTHCARE V3 — SYNCHRONIZATION (critical)

### 12.1 Why two prototypes exist

The employer product prototype ships in **two parallel variants**:

- **Main V3** — the general/mixed-industry demo (`visual-v3.html` and companions). Its demo data
  spans multiple event types (Healthcare, Technology, Diversity, Veterans) and mixed job titles.
- **Healthcare V3** — the healthcare-vertical demo (`visual-v3-healthcare.html` and companions).
  Same product, same components, same interactions; the **data layer** is healthcare (Registered
  Nurse, Medical Assistant, Licensed Practical Nurse, healthcare event names) and every internal
  link points at the `-healthcare` companions.

They exist because JobFairX sells into verticals, and a healthcare buyer should see a healthcare
demo. **They are companion prototypes of one product, not two projects.**

### 12.2 The file pairs

| Main V3 | Healthcare V3 | Role |
|---|---|---|
| `visual-v3.html` | `visual-v3-healthcare.html` | Employer dashboard (events, candidates, interviews, messages, automations, analytics) |
| `lobby-v3.html` | `lobby-v3-healthcare.html` | Event-day lobby (queues, prep checklist, call surface) |
| `setup-flow-v3.html` | `setup-flow-v3-healthcare.html` | Registration / setup flow incl. Interview Settings |

| `interview-screen-v3.html` | `interview-screen-v3-healthcare.html` | The interview screen itself |
| *(shared)* | | `share-preview.html`, `employer-signin-role-gate.html`, `jobseeker-dashboard-pills.html` |

### 12.3 The synchronization rule

**Whenever either variant is improved, the same improvement must be evaluated for the other before
the work is considered complete.** Concretely:

1. **Structural, component, interaction, and copy changes propagate.** A new column, a renamed
   label, a fixed bug, a new state, a restyled chip — all belong in both.
2. **Data does not propagate literally; it is re-expressed per vertical.** A new event row in
   Healthcare V3 becomes an equivalent row in Main V3 with mixed-industry data (and vice versa).
3. **Internal links must stay within the variant.** Healthcare pages link to `-healthcare`
   companions and pass the same query params (`?method=`, `?event=`, `?tab=`). A cross-linked page
   is a bug.
4. **JS data maps are part of the contract.** `EVENT_METHOD` / `NAME_METHOD` / `EVENT_ADDR` /
   `EVENT_URL` are keyed per event; adding a row without adding its key silently renders the wrong
   thing (§5.14, §9.4).
5. **When you finish a change in one variant, state explicitly in your reply whether it was
   applied to the other, and if not, why.**

## 15. Design philosophy (what must stay true)

1. **Static designed-state.** The page you author is the page the user sees. No motion (§9.1). No
   JS-dependent reveals — they ship invisible through the static pipeline.
2. **Product truth over marketing convenience.** Every mock reflects the real application or the
   design about to launch. When they conflict with a marketing claim, flag it (as with the 66% vs
   84% attendance figure) rather than silently inventing.
3. **Outcome first, mechanic underneath.** Headings sell what the employer gets; bodies teach the
   request→accept model in plain words.
4. **Enterprise calm.** Typography, real UI, and honest numbers — not animation, stock photography,
   or template flourishes.
5. **One story, two pages.** The homepage is the brand story; the event page is the conversion page
   that must stand alone for traffic that never saw the homepage.
6. **Both V3 prototypes are one product.** Consistency of experience across them is a feature.

**Interviewers:** added by email; the owner is free ("won't count toward your interviewer seats");
seat metering ("Growth package · 1 of 5 interviewer seats used"); an updates-recipients list; an

**Candidates pipeline filters:** All / Requested / Scheduled / Interviewed / No-show / Declined.
Post-interview feedback: **Yes / Maybe / No**.

**Interviews view:** tabs Upcoming / Pending / Past with counts. Row statuses that exist in the
app: *Awaiting your response, Confirmed, Interviewed, No-show, Declined, Returned to lobby*. The

site but do not exist in the app** — never reuse marketing copy as product truth.

**Automations:** 5 presets — Message new candidates / Message scheduled candidates / Email declined
candidates / Missed interview follow-up / Post-interview follow-up. Setup = trigger → job scope →
rich-text template with merge fields `{CANDIDATE_FIRSTNAME} {JOB_TITLE} {COMPANY} {RECRUITER_NAME}
{INTERVIEW_TIME}` → optional external link → name → Turn on.

**Analytics:** retrospective only. Date-range picker (page-level, scopes cards + chart + table);
granularity is chart-level (Event day / Day / Week / Month) and changes no card. Metrics available:
Interviews scheduled, Interviews completed, Missed interviews, Marked yes, Marked maybe, Marked no,

fractional. **The app does NOT track hires.**

## 25. UX decisions

- **Navigation:** Upcoming Hiring Events · Pricing · FAQ · Contact Us · Sign In · Register for an
  Event. Sign In / Register are app destinations.
- **Sign-in flow (new this session):** clicking Sign In from the employer page hits a **role gate**
  before any auth method — Google, Microsoft *and* email all sit behind it. Employer → sign-in card
  + `localStorage.jfxRole` remembers the choice and skips the question next visit. Job seeker →
  interstitial → redirect. **Recommended backstop documented in the page for the developer:** a
  device flag can't recognise an employer on a new device or in incognito, so after the provider
  returns, if the account already exists, sign in with no question — only ask the role question
  when a **new** employer account is about to be created.
- **Information hierarchy on the two marketing pages:** the homepage is the brand story; the event
  page must stand alone for ad/search traffic that never saw the homepage, so its unique proof
  (testimonials, Past Companies, FAQ, urgency) sits **above** the shared explainer.
- **CTA placement:** every How It Works step carries a CTA except step 3 (Event day) — a gap worth
  closing. The two dark CTA bands were removed at Scott's instruction.
- **Empty states** (prototype pattern): illustration + a plain statement, no subtext where the
  statement suffices; tab-specific empty states keep cross-tab signal as text only.
- **Mobile:** the marketing pages are responsive (the calendar mock switches to the launching
  design's own card layout below 820px). The role gate uses one rule set driving both a real
  `@media (max-width:480px)` and a dev toggle. `employer-home-mobile.html` is a **separate mobile
  design file** built by another session — not a media-query variant.
- **Loading/error states:** none authored on the marketing pages (static). The role gate's only
  transient state is the 1.2s seeker interstitial.

## 26. Technical decisions

- **No build step, no framework** on the marketing pages beyond the Python builders. No JS
  dependency for anything the user must see — **JS-dependent markup ships dead** through the static
  pipeline (this caused the 82,000px event-page disaster in a prior session).
- **Native elements over JS:** the event FAQ is `<details>/<summary>`.
- **Scoped embedding:** foreign designs are embedded under a scoped ID with their own inlined
  tokens (`#jfx-cal`, `#jfx-rev`) so two design systems can coexist without collision.
- **Extraction over imitation:** when a design must match, parse and lift its real CSS rules rather
  than approximating them (§5.12).
- **Libraries intentionally avoided:** jQuery, Bootstrap, wow.js, GSAP, AOS, Swiper — all seen on
  the reference site Scott admired, all rejected with the motion decision (§9.1).
- **Fonts:** self-hosted Inter under `fonts/Inter/`; the app CSS's font URLs are rewritten by the
  home builder (`../../../fonts/` → `../../fonts/`).
- **Cache discipline:** stylesheet links carry `?v=N`; screenshots carry `?v=N`. Bump on change.
- **Verification is scripted, not eyeballed:** count-asserted substitutions, tag-balance deltas
  against the pristine file, md5 comparisons for no-cascade proof, DOM measurement at three widths.
